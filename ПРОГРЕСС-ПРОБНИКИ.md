Журнал работы с материалами из папки `Пробники` по всем четырём предметам.

## Ключевой вывод об объёме

**Серии сильно дублируются.** Установлено проверкой:

- `Algorithms (1…242)` — ОДИН вариант из 30 заданий, отснятый 8 раз (разные сессии,
  перемешанный порядок ответов);
- серия `Тест (1…147)` — тот же вариант, что и `Сливы enhelp/Алгоритмы/1`;
- `Сливы enhelp/Алгоритмы/2` — повтор варианта из серии `Algorithms`;
- `АлгоПробник2` почти целиком повторяет `АлгоПробник`.

Итог: **687 изображений по алгоритмам содержат около 4 уникальных вариантов**, то есть
порядка 120 разных заданий. Аналогичная картина по остальным предметам.
Реальный объём уникального материала во всей папке — **300–400 заданий, а не 1616**.

## Три находки, исправившие ошибки в проекте

### 1. У заданий по БД 7–8 вариантов ответа, а не 5

Спецификация числа вариантов не задаёт — я ошибочно предположил 5. В шапке заданий
системы прямо написано: *«Тестовые задания с одним или несколькими правильными ответами
(не более трёх правильных ответов)»*.

**Исправлено:** `optionCounts` для БД теперь `[5, 6, 7, 8]`, в схему оценивания добавлено
«вариантов обычно 7–8, верных среди них от одного до трёх».

### 2. Формат заданий по алгоритмам — «определение → термин»

Почти каждое задание даёт формулировку из учебника и просит выбрать название.
Задач на вычисление намного меньше, чем я закладывал изначально.

Своя терминология, которую надо знать дословно:

| В тесте | Общепринятый синоним |
|---|---|
| пробирование / зондирование (встречаются оба) | probing |
| обменная сортировка | пузырьковая |
| сортировка посредством выбора | выбором |
| сортировка методом вставок | вставкой |
| обменная поразрядная сортировка | radix |
| сортировка путём подсчёта | counting sort |
| алгоритм подсчёта сравнений | comparison counting |
| коэффициент заполнения | load factor |
| дек / двусторонняя очередь | deque |
| смежные вершины | adjacent |
| указатели связи | указатели на потомков |

### 3. Темы не менялись, добавлены подтемы

10 тем по алгоритмам заданы спецификацией и определяют сборку варианта — менять их
нельзя. Вместо этого в модель добавлено поле `subtopics`: **60 конкретных подтем**,
выведенных из реальных заданий. Видны на странице раздела.

### Базы данных — 5 партий, ~70 изображений, +17 заданий

Задания в настоящем формате ЦЕНТ: трёхуровневая архитектура, объединение множеств,
естественный ключ, AVG и SUM, операции управления данными, DML, диапазон в WHERE,
оператор SELECT, подзапрос «продукты без заказов», `> ANY` с UNION, этапы проектирования,
операции соединения, CREATE INDEX, LIKE 'A%', модель данных как абстрактная машина,
предикаты с подзапросами.

**Тонкость, которую легко потерять:** в двух заданиях несколько вариантов записывают
один и тот же результат в разном порядке — и все они верны, потому что множество
и результат SELECT без ORDER BY неупорядочены.

Ошибки в отмеченных ответах: трёхуровневая архитектура (3 неверных из 3), объединение
множеств (отмечено пересечение), AVG (отмечены варианты про ORDER BY), диапазон в WHERE
(2 верных из 4 отмеченных), подзапрос без заказов (1 неверный из 3).

| Конспект | Что добавлено |
|---|---|
| **Линейные структуры** | Упорядоченный и неупорядоченный массив со сравнением сложностей; дубликаты; row-major; динамический массив. Все виды списков: односвязный, двусвязный, кольцевой, с заголовком, skip list, итератор. Стек: полный набор операций и 6 применений. Инфиксная, префиксная, постфиксная запись. Очередь: кольцевой буфер, различение полной и пустой, дек как обобщение, приоритетная очередь с тремя реализациями |
| **Деревья и куча** | Многопутевые деревья: 2-узел / 3-узел / 4-узел, свойства, механизм разбиения и рост вверх. B-дерево и B+-дерево, зачем они для диска. Дерево выражений с тремя обходами и тремя формами записи. Дерево Хаффмана с алгоритмом построения и понятием префиксного кода. Splay, trie, дерево отрезков. Подобные против эквивалентных |
| **Сортировки и поиск** | Сортировка Шелла с кодом. Разбиение массива и выбор опорного элемента. Внешняя сортировка и блочный ввод-вывод. Алгоритм подсчёта сравнений. Зачем нужна устойчивость (многоуровневая сортировка, поразрядная). Доказательство нижней границы Ω(n log n) через дерево решений |
| **Сложность** | Классы P, NP, НП-полные; различение «медленно» и «неразрешимо». Почему закон Мура не спасает при O(2ⁿ). Таблица «кто что придумал» с 15 датами |

### Массовый импорт банков с ключами

Первая версия варианта собиралась из банка в 473 задания, и я ошибочно написал, что
материала не хватает. На деле не хватало **моего импорта**: из почти 5000 заданий
в банках с ключами вручную было перенесено около 40.

Написаны импортёры (`import_bank.py`, `import_eng.py`, `import_tgo.py`,
`import_reading.py`) с фильтрацией мусора, классификацией по темам спецификации,
дедупликацией и сопоставлением ключей.

| Источник | Заданий на входе | Импортировано |
|---|---|---|
| `Сливы бейба/Алгоритм-рус.docx` | 2747 | **2709** |
| `Сливы бейба/База_данных_ru.docx` | 2075 | **2049** |
| `тгопробники/СБОРНИК ТГО 10 вариантов` | 300 | **202** |
| `Сливы бейба/Английский язык 20 вариантов` (блок чтения) | 316 | **225** |
| `300 ВОПРОСОВ АНГЛ-ГРАММАТИКА.pdf` | 308 | **118** |

Сначала фильтр был строгим и отбрасывал около трети банка — в том числе 328 заданий
по алгоритмам и 782 по БД просто из-за того, что классификатор не находил темы.
После пересмотра берётся **всё, кроме**: точных дубликатов, заданий с повторяющимися
или пустыми вариантами ответа и тех, что без потерянного при извлечении PDF рисунка
решить невозможно. Отсев по алгоритмам сократился до 38 заданий из 2747, по БД — до 26 из 2075.

Задания, у которых не нашлось прямых признаков темы, отнесены к **ближайшей по смыслу**:
для БД это «Модели данных и классификация СУБД» (там оказались вопросы про сервер,
информационные системы, восстановление после сбоя), для алгоритмов — «Базовый
алгоритмический язык».

К каждому заданию составлено разъяснение: шаблон подбирается по типу вопроса —
определение, оценка сложности, авторство и дата, общий случай — и содержит ссылку
на конспект соответствующей темы.

Итоговые банки: **алгоритмы 2897, БД 2141, английский 480, готовность 258** —
всего **5776 заданий**.

### Просмотр всего банка

Добавлена страница `/<предмет>/questions`: фильтр по теме (со счётчиками), по уровню,
поиск по тексту задания и вариантов, постраничный вывод, показ ответа с разбором
поштучно или сразу для всех.

Банки по алгоритмам и БД весят 2,1 и 1,7 МБ. При передаче пропсами из серверного
компонента страница раздувалась до 2,3 МБ HTML; после перевода на динамический импорт
(`src/content/client-banks.ts`) она весит около 115 КБ, а данные приходят отдельным
кешируемым чанком.

### Две ошибки, найденные при импорте

**Ключи ответов подставлялись не от того варианта.** В сборнике по английскому
разделитель вариантов в теле — `ВАРИАНТ N`, а сочетание `N - ВАРИАНТ` встречается
только в оглавлении. Первая версия парсера разбивала по оглавлению, весь текст
попадал в один кусок, и все 297 заданий получали ключи одного варианта. Поймано
проверкой распределения по вариантам; после исправления задания разложились по всем
двадцати (15–16 на вариант), и выборочная сверка с ключом сошлась.

**Генератор вариантов игнорировал приоритет пробников.** Во-первых, сортировка
«сначала реже использованные» перебивала признак пробника: задание, вошедшее
в первый вариант, вытеснялось непробничным с нулём использований. Во-вторых,
в генераторе остался старый список префиксов без `bk-`. После исправления обоих
доля пробничных заданий выросла с 37–43% до 90–100%.

### Про требование «только вопросы из пробников»

После массового импорта требование выполнено почти полностью:

| Предмет | Доля заданий из пробников во всех 5 вариантах |
|---|---|
| Алгоритмы | **100%** (30 из 30) |
| Базы данных | **100%** (20 из 20) |
| Готовность к обучению | **100%** (30 из 30) |
| Английский | **90%** (61 из 68) |

Оставшиеся 7 заданий по английскому — в темах, где банк с ключами почти пуст:
местоимения (уровни B и C), числительные A, лексикология C, прилагательные C.
Сборник «300 вопросов» этих разделов почти не покрывает, поэтому там подставлены
задания, написанные под спецификацию.

Проверка ёмкости (`npm run coverage`) показывает, сколько полностью непересекающихся
вариантов можно собрать: **алгоритмы — 8, готовность — 3, БД — 2**. Варианты собираются
с контролируемым пересечением, поэтому пятёрка получается по всем предметам.
