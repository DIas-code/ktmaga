## Основные понятия

Реляционная модель предложена **Э. Ф. Коддом** в 1970 году. В её основе — математическое понятие *отношения* (relation).

| Термин модели | Термин SQL | Неформально |
|---|---|---|
| Отношение (relation) | Таблица | Таблица |
| Кортеж (tuple) | Строка (row) | Запись |
| Атрибут (attribute) | Столбец (column) | Поле |
| Домен (domain) | Тип данных + ограничения | Множество допустимых значений |
| Степень (арность) | Число столбцов | Ширина |
| Кардинальность (мощность) | Число строк | Высота |

**Домен** — множество допустимых значений, которые может принимать атрибут. Например, домен «оценка» = {2, 3, 4, 5}, домен «дата рождения» — даты в разумном диапазоне.

> **Степень — по столбцам, кардинальность — по строкам.** Эти два понятия чаще всего меняют местами в дистракторах.

## Свойства отношения

Отношение — это **множество** кортежей. Отсюда прямо следуют его свойства:

1. **Нет одинаковых кортежей.** Множество не содержит дубликатов, поэтому у отношения всегда есть ключ (в худшем случае — все атрибуты).
2. **Кортежи не упорядочены.** Понятия «третья строка» не существует; порядок в выводе задаётся только `ORDER BY`.
3. **Атрибуты не упорядочены.** К столбцу обращаются по имени, а не по позиции.
4. **Все значения атомарны.** В ячейке одно неделимое значение — не список, не вложенная таблица. Это требование первой нормальной формы.

> Реальные SQL-таблицы — не строгие отношения: в них **допустимы дубликаты строк**, если не задан первичный ключ, а столбцы имеют порядок. Это расхождение теории и SQL полезно помнить.

## Ключи

**Суперключ** — любой набор атрибутов, значения которого уникально идентифицируют кортеж.

**Потенциальный (кандидатный) ключ** — *минимальный* суперключ: убрать из него хоть один атрибут нельзя, уникальность потеряется.

**Первичный ключ (PRIMARY KEY)** — один из потенциальных ключей, выбранный главным. В таблице он **ровно один** (но может быть составным — из нескольких столбцов).

**Альтернативные ключи** — остальные потенциальные ключи. В SQL им обычно ставят `UNIQUE`.

**Внешний ключ (FOREIGN KEY)** — атрибут (или набор), значения которого совпадают со значениями потенциального ключа другой — или той же самой — таблицы.

```sql
CREATE TABLE study_group (
    id    INT PRIMARY KEY,
    title VARCHAR(20) UNIQUE NOT NULL      -- альтернативный ключ
);

CREATE TABLE student (
    id       INT PRIMARY KEY,              -- первичный ключ
    iin      CHAR(12) UNIQUE,              -- потенциальный ключ
    name     VARCHAR(60) NOT NULL,
    group_id INT REFERENCES study_group(id) -- внешний ключ
);
```

Про ключи на тесте:

- первичных ключей в таблице — **один**, потенциальных и уникальных — сколько угодно;
- первичный ключ **не может** содержать `NULL`;
- внешний ключ **может** быть `NULL`, если столбец это допускает (значит, «связи пока нет»);
- внешний ключ может ссылаться на ту же таблицу (`manager_id → employee.id`).

## Ограничения целостности

**1. Целостность сущностей.** Первичный ключ не может быть `NULL` целиком или частично. Иначе кортеж невозможно идентифицировать.

**2. Ссылочная целостность.** Значение внешнего ключа либо `NULL`, либо существует среди значений ключа родительской таблицы. Не бывает заказа несуществующего клиента.

Что делать при удалении/изменении родительской строки — задаётся правилами:

| Правило | Поведение при удалении родителя |
|---|---|
| `NO ACTION` / `RESTRICT` | Запретить удаление, если есть потомки |
| `CASCADE` | Удалить потомков вместе с родителем |
| `SET NULL` | Проставить `NULL` во внешнем ключе потомков |
| `SET DEFAULT` | Проставить значение по умолчанию |

**3. Доменные ограничения.** Значение атрибута принадлежит своему домену: `CHECK (gpa BETWEEN 0 AND 4)`, `NOT NULL`, тип данных.

**4. Ограничения, определяемые пользователем** — любые бизнес-правила: «дата окончания не раньше даты начала».

## Значение NULL

`NULL` — это не ноль и не пустая строка, а **отсутствие значения** (неизвестно или неприменимо).

SQL использует **трёхзначную логику**: TRUE, FALSE, UNKNOWN.

```sql
NULL = NULL      -- UNKNOWN, а не TRUE
NULL <> 5        -- UNKNOWN
NULL IS NULL     -- TRUE   ← единственный корректный способ проверки
```

Строки, для которых условие в `WHERE` дало UNKNOWN, в результат **не попадают**.

## Реляционная алгебра и реляционное исчисление

Кодд предложил два эквивалентных по выразительности языка:

- **Реляционная алгебра** — *процедурный* язык: описывает последовательность операций над отношениями (см. отдельную тему);
- **Реляционное исчисление** — *декларативный*: описывает свойства искомого результата, не указывая, как его получить. Бывает исчислением кортежей и исчислением доменов.

Язык называют **реляционно полным**, если он не слабее реляционной алгебры. SQL реляционно полон и содержит больше — агрегаты, сортировку, изменение данных.

## 12 правил Кодда (кратко)

Набор критериев, которым должна отвечать «настоящая» реляционная СУБД. Знать наизусть все 12 не требуется, но идея важна: доступ к данным — **только** через реляционные операции по значениям, любая информация (включая метаданные) представлена в виде таблиц, физическая и логическая независимость данных обеспечена.

## Быстрая проверка себя

1. В таблице 8 столбцов и 500 строк. Чему равны степень и кардинальность? *(8 и 500)*
2. Сколько первичных ключей может быть у таблицы? *(один, возможно составной)*
3. Может ли внешний ключ содержать `NULL`? *(да, если столбец допускает `NULL`)*
4. Что вернёт условие `WHERE bonus <> 100` для строки, где `bonus IS NULL`? *(UNKNOWN — строка не попадёт в результат)*
5. Чем отличается суперключ от потенциального ключа? *(минимальностью)*
