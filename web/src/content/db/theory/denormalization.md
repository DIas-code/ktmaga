## Что это и когда применяется

**Денормализация** — осознанное внесение избыточности в нормализованную схему ради **скорости чтения**.

Ключевое слово — *осознанное*. Денормализация:

- выполняется **после** нормализации, а не вместо неё;
- применяется по конкретной **измеренной** причине (профилирование показало, что соединения — узкое место);
- всегда является **компромиссом**: быстрее чтение — сложнее поддержание согласованности.

**Типичные поводы:**

- запрос с 5–7 соединениями выполняется на каждой загрузке страницы;
- аналитические отчёты пересчитывают одни и те же агрегаты;
- нагрузка сильно смещена в сторону чтения (соотношение чтений к записям 100:1 и выше).

## Приёмы денормализации

### 1. Дублирование столбца из справочника

```sql
-- Было: нужно соединение, чтобы показать название товара
SELECT oi.qty, p.title
FROM order_item oi JOIN product p ON p.id = oi.product_id;

-- Стало: название продублировано в строке заказа
ALTER TABLE order_item ADD COLUMN product_title VARCHAR(200);
SELECT qty, product_title FROM order_item;
```

Бонус: в заказе сохраняется **историческое** название на момент покупки, даже если товар потом переименуют.

### 2. Хранение предвычисленных агрегатов

```sql
ALTER TABLE "order" ADD COLUMN total_amount NUMERIC(12,2);
ALTER TABLE post  ADD COLUMN comment_count INT DEFAULT 0;
```

Вместо `SUM` по всем позициям при каждом чтении — готовое поле, обновляемое триггером или кодом приложения.

### 3. Объединение таблиц 1:1

Если `Сотрудник` и `АнкетаСотрудника` всегда читаются вместе и обе стороны обязательны, разделение даёт только лишнее соединение.

### 4. Материализованные представления

```sql
CREATE MATERIALIZED VIEW mv_sales_by_month AS
SELECT date_trunc('month', sold_at) AS m, SUM(amount) AS total
FROM sale
GROUP BY 1;

REFRESH MATERIALIZED VIEW mv_sales_by_month;
```

В отличие от обычного `VIEW`, результат физически хранится и требует обновления.

### 5. Хранение производных и «плоских» значений

Полное имя рядом с частями, признак `is_active` вместо вычисления по датам, «плоский» путь в иерархии вместо рекурсивного обхода.

> **Не является денормализацией:** разбиение таблицы на несколько более узких, создание индекса, партиционирование по датам. Разбиение — движение в сторону нормализации; индекс избыточности данных не создаёт.

## Издержки

| Издержка | В чём проявляется |
|---|---|
| Рост объёма | Одни и те же данные хранятся в нескольких местах |
| Риск рассогласования | Обновили в одном месте, забыли в другом |
| Усложнение записи | Каждая запись обновляет несколько таблиц |
| Сложность кода | Нужны триггеры, регламентные пересчёты, проверки |
| Возврат аномалий | Аномалии обновления, ради устранения которых нормализовали |

**Скорость выборок при этом расти должна** — ради этого всё и делается. Вариант «выборки замедляются» в тестах неверен.

## Поддержание согласованности

**Триггеры** — пересчёт синхронно с изменением:

```sql
CREATE TRIGGER trg_order_total
AFTER INSERT OR UPDATE OR DELETE ON order_item
FOR EACH ROW EXECUTE FUNCTION recalc_order_total();
```

**Регламентный пересчёт** — по расписанию, если допустима задержка.

**Логика приложения** — самый хрупкий вариант: любой обход мимо приложения (миграция, ручной `UPDATE`) ломает согласованность.

## Денормализация в хранилищах данных

Аналитические системы (OLAP) денормализованы по умолчанию — они оптимизированы под чтение.

### Схема «звезда»

- В центре — **таблица фактов** (продажи, транзакции): много строк, числовые меры и внешние ключи.
- Вокруг — **таблицы измерений** (товар, клиент, дата, магазин): плоские, намеренно **не приведённые к 3НФ**.

```
        Измерение_Дата
              |
Изм_Товар — ФАКТ_Продажи — Изм_Клиент
              |
        Измерение_Магазин
```

Каждое измерение соединяется с фактами одним соединением — отсюда скорость.

### Схема «снежинка»

То же самое, но измерения **нормализованы**: `Товар → Категория → Раздел` разворачивается в цепочку справочников.

| | «Звезда» | «Снежинка» |
|---|---|---|
| Измерения | Денормализованы | Нормализованы |
| Число соединений | Меньше | Больше |
| Объём | Больше (избыточность) | Меньше |
| Скорость запросов | Выше | Ниже |
| Целостность | Ниже | Выше |

> «Звезда» **менее** нормализована, чем «снежинка». Обратное утверждение — стандартный дистрактор.

## OLTP против OLAP

| | OLTP | OLAP |
|---|---|---|
| Назначение | Операционные транзакции | Аналитика и отчётность |
| Нагрузка | Много коротких записей | Много тяжёлых чтений |
| Схема | Нормализованная (3НФ) | Денормализованная («звезда») |
| Запросы | Точечные, по ключу | Агрегирующие, по большим объёмам |

## Правило выбора

1. Спроектировать нормализованную схему (3НФ) — это база.
2. Измерить производительность на реальных данных.
3. Сначала попробовать дешёвые средства: **индексы**, переписать запрос, кеш.
4. Денормализовать **точечно** — только там, где измерения показали проблему.
5. Сразу продумать, чем поддерживать согласованность.

## Быстрая проверка себя

1. Что происходит с объёмом данных при денормализации? *(растёт)*
2. Что происходит со скоростью выборок? *(растёт — ради этого и делается)*
3. Что нормализованнее — «звезда» или «снежинка»? *(«снежинка»)*
4. Является ли создание индекса денормализацией? *(нет)*
5. Что делают до денормализации? *(нормализуют схему и измеряют производительность)*
