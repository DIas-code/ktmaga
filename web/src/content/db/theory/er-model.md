## Место ER-модели в проектировании

Проектирование БД идёт в три этапа:

1. **Концептуальное** — ER-диаграмма. Независимо от СУБД: что за объекты, как связаны.
2. **Логическое** — переход к реляционной схеме: таблицы, ключи, нормализация.
3. **Физическое** — типы данных конкретной СУБД, индексы, размещение файлов.

ER-модель (Entity — Relationship, П. Чен, 1976) — язык первого этапа.

## Элементы ER-диаграммы (нотация Чена)

| Фигура | Что обозначает |
|---|---|
| **Прямоугольник** | Сущность (Entity) |
| **Двойной прямоугольник** | Слабая сущность |
| **Ромб** | Связь (Relationship) |
| **Двойной ромб** | Идентифицирующая связь |
| **Овал** | Атрибут |
| **Подчёркнутый овал** | Ключевой атрибут |
| **Двойной овал** | Многозначный атрибут |
| **Пунктирный овал** | Производный (вычисляемый) атрибут |
| **Овал с овалами внутри** | Составной атрибут |

> Это готовый набор вопросов на соответствие. Запомните минимум: **прямоугольник — сущность, ромб — связь, овал — атрибут**.

## Сущности и атрибуты

**Сущность** — объект, о котором надо хранить данные (Студент, Курс, Отдел). Различают:
- **тип сущности** (Студент вообще) и
- **экземпляр** (конкретный Студент Айгуль).

**Виды атрибутов:**

- **простой** — неделимый (`gpa`);
- **составной** — из частей (`ФИО` = фамилия + имя + отчество);
- **многозначный** — несколько значений у одного экземпляра (`телефоны`);
- **производный** — вычисляется из других (`возраст` из `даты рождения`);
- **ключевой** — идентифицирует экземпляр.

## Связи: мощность и участие

**Мощность (кардинальность)** связи — сколько экземпляров одной сущности может быть связано с экземпляром другой:

| Тип | Пример |
|---|---|
| **1:1** | Сотрудник — Личный кабинет |
| **1:М** | Отдел — Сотрудники |
| **М:М** | Студенты — Курсы |

**Степень связи** — сколько сущностей она соединяет: бинарная (2), тернарная (3), унарная/рекурсивная (1, сущность связана сама с собой — «сотрудник — руководитель»).

**Класс участия (обязательность):**

- **обязательное (тотальное)** — каждый экземпляр обязан участвовать в связи (у каждого заказа есть клиент);
- **необязательное (частичное)** — может не участвовать (не у каждого сотрудника есть подчинённые).

## Слабые сущности

**Слабая сущность** не имеет собственного достаточного первичного ключа и не существует без «владельца».

- Идентифицируется через **идентифицирующую связь** с сильной сущностью.
- Её ключ = **частичный ключ** + ключ владельца.
- Рисуется двойным прямоугольником.

**Пример:** `СтрокаЗаказа` не существует без `Заказ`. Её ключ — (`номер_заказа`, `номер_позиции`).

## Переход от ER к реляционной схеме

Это самая проверяемая на тесте часть.

### 1. Каждая сильная сущность → таблица

Атрибуты становятся столбцами, ключевой атрибут — `PRIMARY KEY`.

### 2. Связь 1:М → внешний ключ на стороне «многие»

```sql
CREATE TABLE dept (
    id    INT PRIMARY KEY,
    title VARCHAR(60) NOT NULL
);

CREATE TABLE employee (
    id      INT PRIMARY KEY,
    name    VARCHAR(60) NOT NULL,
    dept_id INT NOT NULL REFERENCES dept(id)   -- FK на стороне «многие»
);
```

> **Правило, которое надо помнить дословно:** внешний ключ всегда помещается на стороне «многие». Каждый сотрудник ссылается на свой отдел, а не наоборот — иначе в отделе пришлось бы хранить список сотрудников в одной ячейке, что нарушает 1НФ.

### 3. Связь М:М → отдельная связующая таблица

```sql
CREATE TABLE enrollment (
    student_id INT REFERENCES student(id),
    course_id  INT REFERENCES course(id),
    grade      SMALLINT,                       -- атрибут самой связи
    PRIMARY KEY (student_id, course_id)        -- составной ключ
);
```

Связующая (ассоциативная) таблица содержит внешние ключи на обе сущности; их пара обычно и становится первичным ключом. Собственные атрибуты связи (оценка, дата) живут здесь же.

### 4. Связь 1:1 → внешний ключ с UNIQUE в одной из таблиц

Помещается в таблицу с **обязательным** участием. Если обе стороны обязательны, таблицы часто объединяют в одну.

### 5. Многозначный атрибут → отдельная таблица

`телефоны` студента превращаются в `student_phone(student_id, phone)`.

### 6. Слабая сущность → таблица с составным ключом

Ключ владельца входит в первичный ключ слабой сущности, обычно с `ON DELETE CASCADE`.

### Сводка

| Конструкция ER | Реляционная реализация |
|---|---|
| Сущность | Таблица |
| Атрибут | Столбец |
| Ключевой атрибут | `PRIMARY KEY` |
| Связь 1:1 | FK + `UNIQUE` |
| Связь 1:М | FK на стороне «многие» |
| Связь М:М | Связующая таблица с составным ключом |
| Многозначный атрибут | Отдельная таблица |
| Слабая сущность | Таблица, ключ = ключ владельца + частичный ключ |

## Нотация «воронья лапка» (Crow's foot)

В инструментах моделирования чаще встречается она, а не нотация Чена:

- сущность — прямоугольник с перечнем атрибутов;
- «лапка» (три черточки) на конце линии — сторона «многие»;
- одна черта — «один»;
- кружок — необязательное участие (ноль);
- две черты — обязательное участие.

Сочетания читаются справа налево: `○|` = «ноль или один», `|<` = «один или много».

## Быстрая проверка себя

1. Где размещается внешний ключ при связи 1:М? *(на стороне «многие»)*
2. Сколько таблиц потребуется для связи М:М между двумя сущностями? *(три: две сущности + связующая)*
3. Чем изображается связь в нотации Чена? *(ромбом)*
4. Может ли слабая сущность существовать без владельца? *(нет)*
5. Куда девается многозначный атрибут при переходе к реляционной схеме? *(в отдельную таблицу)*
