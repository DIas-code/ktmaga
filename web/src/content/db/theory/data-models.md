## Что такое база данных и СУБД

**База данных (БД)** — организованная совокупность взаимосвязанных данных, хранимая по единым правилам и описываемая некоторой моделью.

**СУБД** — программный комплекс, который управляет доступом к этим данным. Её задачи:

- хранение данных и организация доступа к ним;
- поддержка целостности (данные остаются согласованными);
- управление транзакциями и параллельным доступом многих пользователей;
- разграничение прав;
- резервное копирование и восстановление.

> Компиляция прикладных программ, отрисовка интерфейса и передача данных по сети — **не** функции СУБД. Этот вариант часто подсовывают в тестах.

## Модель данных

**Модель данных** — набор понятий и правил, которыми описывается структура данных, допустимые операции над ними и ограничения целостности. Три составляющие любой модели:

1. **структурная** — из чего строятся данные (таблицы? деревья? документы?);
2. **манипуляционная** — какие операции допустимы (реляционная алгебра, SQL);
3. **целостная** — какие ограничения обязаны выполняться.

## Классификация моделей данных

| Поколение | Модель | Как устроена | Примеры |
|---|---|---|---|
| Дореляционные | Инвертированных списков | Плоские файлы + индексы | Datacom/DB, Adabas |
| Дореляционные | **Иерархическая** | Дерево: у записи один родитель | IMS (IBM) |
| Дореляционные | **Сетевая** (CODASYL) | Граф: у записи может быть несколько родителей | IDMS, db_VISTA |
| Реляционные | **Реляционная** | Отношения = таблицы, связи по значениям ключей | Oracle, PostgreSQL, MySQL, MS SQL Server |
| Постреляционные | Объектно-ориентированная | Объекты с наследованием и методами | ObjectStore, db4o |
| Постреляционные | Объектно-реляционная | Реляционная + пользовательские типы и наследование | PostgreSQL, Oracle |
| NoSQL | Документная | JSON/BSON-документы | MongoDB, CouchDB |
| NoSQL | «Ключ — значение» | Ассоциативный массив | Redis, DynamoDB |
| NoSQL | Колоночная | Хранение по столбцам | Cassandra, HBase |
| NoSQL | Графовая | Вершины и рёбра как первоклассные объекты | Neo4j |

**Что надо чётко разделять на тесте:**

- иерархическая, сетевая, инвертированных списков — **дореляционные**;
- реляционная — Кодд, 1970 год;
- объектно-ориентированная, объектно-реляционная — **постреляционные**;
- MongoDB, Redis, Cassandra, Neo4j — **не реляционные** СУБД.

### Иерархическая vs сетевая

- **Иерархическая**: строгое дерево. Каждая запись-потомок имеет ровно одного предка. Связь «многие ко многим» напрямую невыразима — приходится дублировать данные.
- **Сетевая**: обобщение иерархической. Потомок может иметь несколько предков, поэтому М:М выражается. Плата — сложность навигации: программист вручную «ходит» по связям.

Обе требуют **навигационного** доступа: программа сама указывает путь к данным. Реляционная модель этим и хороша — доступ **декларативный**: вы описываете, *что* нужно, а не *как* это найти.

## Классификация СУБД

**По модели данных:** иерархические, сетевые, реляционные, объектно-ориентированные, документные и т. д. (см. таблицу выше).

**По архитектуре:**

- **файл-серверные** — файл БД лежит на общем ресурсе, обработка идёт на клиенте (Microsoft Access, dBase). Плохо масштабируются;
- **клиент-серверные** — сервер СУБД принимает запросы и возвращает результат (PostgreSQL, Oracle, MySQL);
- **встраиваемые** — библиотека внутри приложения, без отдельного процесса (SQLite, H2).

**По степени распределённости:** локальные (на одном узле) и распределённые (данные разнесены по узлам).

## Трёхуровневая архитектура ANSI/SPARC

Стандартная схема организации СУБД — три уровня описания одних и тех же данных:

| Уровень | Что описывает | Кто работает |
|---|---|---|
| **Внешний** | Представления отдельных пользователей и приложений (подсхемы, VIEW) | Прикладной программист, пользователь |
| **Концептуальный** | Логическая схема всей БД: сущности, атрибуты, связи, ограничения | Администратор данных |
| **Внутренний** | Физическое хранение: файлы, страницы, индексы, сжатие | Администратор БД, сама СУБД |

Смысл разделения — **независимость данных**:

- **логическая независимость** — изменения концептуальной схемы (добавили столбец) не ломают внешние представления;
- **физическая независимость** — изменения способа хранения (построили индекс, сменили файловую организацию) не затрагивают логическую схему и запросы.

> Не путайте с уровнями модели OSI (транспортный, сеансовый, канальный) — к архитектуре БД они отношения не имеют, но именно их подставляют в дистракторы.

## Архитектура «клиент — сервер» и трёхуровневая архитектура

Не путать с трёхуровневой архитектурой ANSI/SPARC — это про другое.

**Двухзвенная (клиент — сервер):** клиент содержит и интерфейс, и логику приложения,
сервер хранит данные. Логика дублируется на каждом клиенте, обновлять тяжело.

**Трёхзвенная (трёхуровневая):**

| Уровень | Что делает |
|---|---|
| **Представления** | Пользовательский интерфейс |
| **Приложений** | Реализация прикладных алгоритмов и средств обработки данных |
| **Данных** | СУБД, в которой хранятся данные |

Выигрыш: логика живёт в одном месте, клиенты становятся «тонкими», систему проще
масштабировать и обновлять.

> Масштабируемость — это СВОЙСТВО такой архитектуры, а не её уровень.
> В тестовых заданиях «уровень масштабируемости», «уровень соединения», «уровень отправки»
> подставляют как правдоподобные, но несуществующие варианты.

## Кто и когда

| Событие | Кто | Год |
|---|---|---|
| Реляционная модель | Эдгар Франк Кодд (IBM) | 1970 |
| Язык SEQUEL, позже SQL | Дональд Чемберлин, Реймонд Бойс (IBM) | 1974 |
| Нормальная форма Бойса — Кодда | Реймонд Бойс, Эдгар Кодд | 1974 |
| ER-модель «сущность — связь» | Питер Чен | 1976 |
| Первая коммерческая СУБД с SQL — Oracle | Ларри Эллисон и соавторы | 1979 |
| IBM SQL/DS на основе прототипа System R | IBM | 1981 |
| Начало работы ANSI над стандартом SQL | ANSI | 1982 |
| Утверждение стандарта SQL-86 | ANSI | 1986 |
| Редакция SQL-92 | ANSI / ISO | 1992 |
| Редакция SQL:1999 (рекурсия, триггеры) | ANSI / ISO | 1999 |

Название SEQUEL пришлось сменить на SQL из-за чужого товарного знака.
Конкурирующим языком того времени был QUEL из проекта Ingres (Беркли),
а QBE (Query by Example) — ещё одна разработка IBM.

## Пользователи БД

- **конечные пользователи** — работают через приложение;
- **прикладные программисты** — пишут приложения поверх БД;
- **администратор данных (DA)** — отвечает за логическую схему и стандарты;
- **администратор БД (DBA)** — за физическую реализацию, производительность, резервные копии, права.

## Быстрая проверка себя

1. К какому поколению относится сетевая модель? *(дореляционное)*
2. Может ли иерархическая модель напрямую выразить связь «многие ко многим»? *(нет)*
3. Что даёт разделение концептуального и внутреннего уровней? *(физическую независимость данных)*
4. Redis — реляционная СУБД? *(нет, хранилище «ключ — значение»)*
5. Кто и когда предложил реляционную модель? *(Э. Ф. Кодд, 1970)*
